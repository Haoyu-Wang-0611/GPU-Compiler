# 1. 输入：一个 affine.mlir

```mlir
func.func @gemm512(%A: memref<512x512xf32>,
                   %B: memref<512x512xf32>,
                   %C: memref<512x512xf32>) {
  affine.for %i = 0 to 512 {                 // L0
    affine.for %j = 0 to 512 {               // L1
      affine.for %k = 0 to 512 {             // L2
        %a = affine.load %A[%i, %k]
        %b = affine.load %B[%k, %j]
        %c = affine.load %C[%i, %j]
        %p = arith.mulf %a, %b
        %s = arith.addf %p, %c
        affine.store %s, %C[%i, %j]
      }
    }
  }
  return
}
```

可用信息只有三样：**循环的 trip count**、**每个 load/store 的下标表达式**、**算术 op 的个数**。没有任何运行时信息——这就是"无实测在环"的前提。

# 2. ① 结构分析：窗口法

**动作**：给循环编号（外→内 L0/L1/L2），对每个数组的每一维，找出它的下标里出现了哪个循环、带什么常数偏移。

| 数组         | 维 0      | 维 1      | 结论                         |
| ---------- | -------- | -------- | -------------------------- |
| A `A[i,k]` | L0（偏移 0） | L2（偏移 0） | 窗口 = BM × TK               |
| B `B[k,j]` | L2       | L1       | 窗口 = TK × BN               |
| C `C[i,j]` | L0       | L1       | 窗口 = BM × BN，**写→不进 smem** |

**窗口大小** = `max(携带该维的 tile) + (max偏移 − min偏移)`，再按数组大小封顶。
偏移差就是 halo：stencil 的 `A[i-1]/A[i]/A[i+1]` 会自动得到 `T+2`，**不需要特判**。

**同时得到一个关键量：工作集**

```
W = (M·K + K·N + M·N)·4 = 3 × 512² × 4 = 3 MB
```

这个 3 MB 在后面决定带宽 regime（72 MB 的 L2 装得下）。

显存层次：
	寄存器            每线程 ~255 个（最快）
	共享内存 smem     每 SM 100 KB（你的 tile 放这儿）
	L2 缓存           整卡共享 72 MB        ← 关键
	显存 DRAM         24 GB，约 1000 GB/s

**输出**：每个数组的面板字节 + 工作集 + 哪些面板是"流式"（由归约环携带，要 ×(S+1)）。
**代码**：`L1Feas.cpp` 的窗口收集与 `windowFootprint`（约 `:70-179`）。

> v1.8.3 的面板修正就在这一层：syrk 的 `A[i,k]` 与 `A[j,k]` 是**两块独立面板**，不能合并。旧实现合并成一块 → 以为 80 KB 可行，实际 160 KB。

# 3. ② 结构分类：决定用哪套公式

**动作**：只看两个集合。

- **归约环** = 出现在读下标、但不出现在写下标里的循环 → 本例 = {L2}，**1 个**；
- **输出环** = 出现在写下标里的循环 → {L0, L1}，**2 个且同一层嵌套**。

⇒ 命中 **GEMM 模板**（单个归约 + 两个输出环）。

分类结果决定后面用哪支公式：

| 归约环             | 结构    | 模板                     |
| --------------- | ----- | ---------------------- |
| 0               | 纯流式   | stencil-1D / 2D / 兄弟交换 |
| 1               | 矩阵乘   | **GEMM（本例）**           |
| ≥2，每段 2 输出+1 归约 | 多遍矩阵乘 | 组化链（2mm/3mm）           |
| ≥2，每段 1 输出+1 归约 | 多遍向量链 | GEMV 链（atax/mvt/bicg）  |
| 其它              | 接不住   | 结构化拒因                  |

**代码**：分派逻辑约 `:285-303`。

# 4. ③ 硬可行域（可证明，删候选）

对 96 个枚举（BM/BN∈{64,128,256}² 去 256×256 × TK∈{16,32,64} × S∈{1..4}）逐条检查：

| 约束   | 公式                                                | 本例结果                  |
| ---- | ------------------------------------------------- | --------------------- |
| 共享内存 | `Σ(流式面板) × (S+1) ≤ 99 KB`                         | 96 → **48**           |
| 寄存器  | 每线程 ≤255（实测 96 实例 max 245、0 spill）；`256×256` 直接排除 | 本例 64×64 → 95 个寄存器，安全 |
| 结构   | 模板匹配即可                                            | ✓                     |

**这 48 个是"物理上能跑"的集合**，与载具实际分配逐字节一致（22 份日志审计全过）。

# 5. ④ 搜索空间收缩（经验，不是可行域）

再做一步 `块数 = (512/BM)×(512/BN) ≥ numSms/2 = 64`：

```
48 → 10（只剩 64×64 的 10 个 TK×S 组合）
```

**依据**（三条实测）：
- GEMM 8/8 行决策不变（加不加这条，答案一样）；
- 被收缩掉的配置里**最快的也慢 +69.4%**；
- 收缩后为空时（如 64×64 的小问题）**退回完整可行域**，保证永远有解。

**口径**：可行域只由 容量/寄存器/结构 定义；这一条叫"搜索空间收缩"，不叫可行性。

# 6. ⑤ 成本模型：逐项算给你看

对本例的候选 `BM=BN=64, TK=64, S=2`：

```
chunks = ceil(512/64) = 8
工作集 3 MB ≤ 72 MB → 带宽 = 7.21 × 2 = 14.42 GB/s/SM      ← L2 regime
copy   = (64·64 + 64·64)·4 / 14.42 + 150
       = 32,768/14.42 + 150 = 2,272.4 + 150 = 2,422.4 ns   ← 含 cChunk
comp   = 2·64·64·64 / 630 = 832.2 ns
L_min  = 1,739 ns
block  = 8 × max(2,422.4, 832.2, min(1,739, 3,254.6))
       = 8 × 2,422.4 = 19,379 ns
expo   = max(330 / 2^1.2, 52) = 143.6 ns                   ← 深度摊薄延迟
cWrite = 64·64·4 / 7.21 = 2,272.4 ns                       ← 写回走 DRAM，不 boost
waves  = ceil(64/128) = 1
total  = 3,000 + 21,795 = 24,795 ns ≈ 24.8 µs
```


三个修正分别在哪儿起作用：

| 修正 | 作用点 | 本例效果 |
|---|---|---|
| **cChunk（150 ns，名义值）** | 每 chunk 代价加一项固定开销 → 打破 TK 的退化平局 | 让 `TK=64/S2`（24.8）胜过 `TK=32/S4`（32.6）；没有它两者在模型里只差 86 ns，靠枚举顺序会选 32 |
| **L2 regime（β=2）** | `copy`/`cWrite` 的带宽按工作集切换 | 绝对误差 +72% → **+2.5%**；决策在 β∈[1,4] 内不变 |
| 两态式（S=1 vs S≥2） | 串行 `copy+comp` vs 重叠 `max(copy,comp)` | 本例 S=2 走重叠分支 |

**代码**：`tools/decide_dev.py`（唯一决策入口，`_eval_panels`）。

# 7. ⑥ 决策：argmin 与并列规则

10 个候选打分后取最小：

| 候选 | 预测 | 实测 |
|---|---|---|
| **64/64/64/2** | **24.8 µs** ← 选中 | **24.2 µs** |
| 64/64/64/1 | 31.6 | 24.2（并列） |
| 64/64/32/4 | 32.6 | 25.5 |

决策输出：`BM=64 BN=64 TK=64 Stages=2 predicted=24795 ns [搜索: 可行 10/96]`。

同分时的规则：枚举顺序（BM→BN→TK→S 升序），**写死并文档化**，避免"隐性偏好"。

# 8. ⑦ 发射：把三个参数变成 IR

```
affine-loop-tile(64, 64) on (i, j)                    ← BM/BN
affine-loop-tile(64)    on (k)                        ← TK
transform.loop.pipeline %k iteration_interval = II    ← 深度
   II = ceil(maxCycle / (S-1)) = ceil(3/1) = 3        ← 用依赖链长度反推
```

**已知缺口（必须写进 limitation）**：发射器只设 `iteration_interval`，**没有设 `num_stages`**，所以 IR 里的**缓冲份数不是模型以为的 S+1**。要补的是 `(num_stages, II) ↔ (B, D)` 的映射，做法是 4×2 发射矩阵数 IR 的 smem 分配与克隆数。

# 9. ⑧ oracle 验证：决策有多好

同一候选空间（48 个）在 GPU 上全测一遍（干净卡，20 次平均）：

| 配置 | 实测 |
|---|---|
| **64/64/64/1** | **24.2** ← 并列最优 |
| **64/64/64/2**（我们的选择） | **24.2** |
| 64/64/32/3 | 25.4 |
| 128×256 家族 | 131.2（+445%） |

结论：**rank 1/48，距优 +0.0%，绝对误差 +2.5%**。

同时这一步给出"规则 baseline"的对照：只用约束 + 取最大 tile（`R_full`）在 15 行上中位 +3.0%，而加了三处修正的模型是 **+0.0%**。

# 12. 这套流程的边界（必须知道的四件事）

| 边界 | 现状 |
|---|---|
| **适用域** | 静态 trip count、非融合、五类结构；接不住就明确拒绝 |
| **深度语义** | 发射端还没实现 S（只给了 II）→ 端到端切片前必须先钉死映射 |
| **regime 边界** | 工作集 ≤72 MB 用 L2 带宽；本例 3 MB 属 L2；4096³（192 MB）走 DRAM，误差 −13.9% |
| **泛化** | 15 行都是开发集；留出套件（12 个新 kernel）是唯一的泛化证据 |

---

**一句话收束**：这个研究的全流程是"**把 IR 的结构信息压成三个可判定的量（面板字节、工作集、块数），用可证明的约束砍掉不能跑的，用带物理量纲的公式在剩下的里挑一个，最后用穷举实测反过来审计这个选择**"。gemm512 是这个流程最干净的一例：96 → 48 → 10 → 1，预测 24.8 µs，实测 24.2 µs，rank 1/48。
