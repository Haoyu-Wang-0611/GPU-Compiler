# stencil-1D / heat1d 两行（#18）— 2026-11-18

> 依据：`python tools/replay_dev.py`、heat1d 日志原始表
> 结论一句话：**+18% 不是模型问题，是相对一个"只在 S=4 出现的 6.1 µs 带"算出来的；
> 模型的选择落在主并列带（8 个 cell = 7.2 µs）。已修的是绝对量级，不是差距。**

## 1. 原始实测表（heat1d，N=2²⁰）

| T | S=1 | S=2 | S=3 | S=4 |
|---|---|---|---|---|
| 16 | 169.0 | 145.4 | 142.3 | 146.4 |
| 64 | 44.0 | 37.9 | 36.9 | 37.9 |
| 256 | 16.4 | 13.6 | 14.3 | 13.3 |
| 512 | 10.2 | 9.2 | 9.2 | 9.2 |
| 1024 | 8.2 | 8.2 | 8.2 | 8.2 |
| **2048** | **7.2** | **7.2** | **7.2** | **6.1** |
| **4096** | **7.2** | **7.2** | **7.2** | **6.1** |
| 8192 | 7.2 | 7.2 | — | — |

两个关键事实：

1. **7.2 µs 是主并列带**：8 个 cell（T=1024 全部 S、T=2048/4096 的 S=1..3、T=8192 的 S=1..2）。
2. **6.1 µs 只出现在 S=4 且 T≥2048 的 2 个 cell**，且 S=2/S=3 与 S=1 一样是 7.2。

⇒ 任何"重叠深度"的解释都会预测 S=2 与 S=4 同档；实测只有 S=4 突出。
这不是模型能刻画的效应（更像是某个 S 取值下的代码生成/L2 驻留差异），必须复测。

## 2. 已做的修改（只改量级，不改决策）

stencil-1D 分支此前用 DRAM 带宽（7.21 GB/s/SM）算 copy，但 2²⁰ 的工作集
（A 读 + B 写 = 8 MB）完全在 72 MB L2 内：

| | 预测 | 实测 | 绝对误差 |
|---|---|---|---|
| 修改前 | 12.3 µs | 7.2 µs | **+71%** |
| 修改后（L2 regime） | 7.8 µs | 7.2 µs | **+8.3%** |

决策不变（T=2048 / S=1），距优仍是 +18%（因为"最优"是那 2 个 6.1 的 cell）。

## 3. heat1d 2²⁴ 的另一个发现（写重型 kernel 的模型局限）

2²⁴ 实测最优 98.4 µs，模型预测 150.8 µs（+47%）。但按模型口径的流量
（A 读 67 MB + B 写 67 MB = 134 MB）计算，实测对应 **1.31 TB/s**，
**高于 4090 的 DRAM 峰值**（1.008 TB/s）。说明写回被 L2 吸收、并未全部计入内核计时。
⇒ 对"写重型"kernel，`copy = bytes/BW_DRAM` 会系统性高估；这是模型的已知边界，
应在 limitation 中写明，而不是靠加系数修正。

## 4. 复测判据（R=5 交错时看什么）

| 观察 | 判定 |
|---|---|
| S=4 的 6.1 重现，且 S=3 也降到 6.1 | 真实效应 → 需在模型里加"S≥4 的额外重叠"项 |
| S=4 的 6.1 不复现（回到 7.2） | 该行按 7.2 主并列带报，+18% 从表中消失 |
| 只有 S=4 单独快、S=3 不动 | 代码生成差异，记为"不可建模"，不进入模型 |

## 5. 论文写法

> stencil-1D 的带宽按工作集选择 L2/DRAM regime（2²⁰ 为 L2 驻留，2²⁴ 为 DRAM 流）。
> 在 2²⁰ 上模型的选择落在 8 个并列最优配置（7.2 µs）之中；日志中另有两个
> S=4 的配置测得 6.1 µs，其成因未被任何已建模因素解释，列为待复测项。
