# GEMV 分支的占用守卫：**必要**（与 GEMM 相反）— 2026-11-18

> 结论一句话：GEMM 上守卫冗余（0/8 决策变化），**GEMV 上守卫是承重的**——
> 去掉它，mvt/bicg 会从最优 T=8 掉到 T=16（+31% / +22%）。

## 1. 三个变体的决策

| kernel | G1（守卫 ≥SM/2） | G3（无守卫） | 实测最优 |
|---|---|---|---|
| atax 8192 | T=64/TK64/S1 → **+0.7%** | T=64 → +0.7% | T=64/S=3 |
| **mvt 512** | T=8 → **+0.0%** | **T=16 → +31.3%** | T=8/TK64/S1 |
| **bicg 512** | T=8 → **+0.0%** | **T=16 → +22.3%** | T=8/TK64/S1 |

⇒ G2（≥SM）与 G1 决策相同；**G3 在 mvt/bicg 上退化 22–31%**。

## 2. 为什么（机制：T<16 的"thin"惩罚把排序搞反了）

模型对 GEMV 的每 chunk 下界是 `L_min = 820 ns`，但当 **T<16** 时用 `1260 ns`。
在 N=512 上（chunks=8）：

| T | 块数 | L_min | chunks×L_min | 模型判断 | 实测 |
|---|---|---|---|---|---|
| **8** | **64** | **1260**（thin） | **10,080** | **最慢** | **19.5 µs（最快）** |
| 16 | 32 | 820 | 6,560 | 较快 | 25.6 |
| 32 | 16 | 820 | 6,560 | 较快 | 38.9 |
| 64 | 8 | 820 | 6,560 | 较快 | 39.9 |

**排序被完全颠倒**：模型认为 T=8 最慢，实测它最快。原因是
"T 小 → thin 惩罚大"这条规则在大 N（atax：T=8 确实最差，937 µs）上成立，
但在小 N（mvt/bicg：T=8 恰好给足 64 个块）上不成立。

守卫（块数 ≥ SM/2）正好把 T 限制在 ≤8（N=512 时），于是**替模型兜住了这个错误**。

## 3. 尝试过的修法：波次惩罚（**未采用**）

`total_pass × max(1, SMs/块数)` 能让 G3 恢复 T=8，但它把预测值放大 2 倍，
与实测矛盾：mvt 的 2.1 MB 流量在 19.5 µs 内完成 → 仅 107 GB/s，**远低于带宽峰值**，
说明该 kernel 是**延迟/L_min 受限**，不是吞吐受限。用吞吐惩罚在机理上是错的。
⇒ 代码里保留 `wave_pen` 参数但**默认关闭**，仅作被否证的实验记录。

## 4. 结论与后续

1. **GEMV 的守卫保留**（用户已决定保留全局守卫；GEMV 这边它是承重件，不能删）。
2. 真正的模型缺口登记为待办：`L_min(T<16)=1260` 应按**块数/占用**而不是 T 来判定
   —— 大 N 时 T 小确实差，小 N 时 T 小反而好。修好之后守卫才可能在这一族变成冗余。
3. 论文写法：
   > 对 GEMV 链，块数下限在本版模型中是**必要的**：模型的每 chunk 下界对 T<16 的
   > 惩罚在大 N 上成立、在小 N 上不成立；该下限阻止了模型在小 N 上选择块数不足的配置
   > （无下限时距优 +22%~+31%）。我们把这一依赖关系显式报告，并在留出集上验证。
