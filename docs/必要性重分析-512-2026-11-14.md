# 必要性重分析（第一批日志：512³ ×2）— 2026-11-14

> 输入：`daima/sweep_512.log`、`daima/sweep_512_S4.log`（两份同尺寸独立会话）
> 工具：`tools/necessity.py`（五策略重算）、`tools/l1model.py`（模型复现）
> 零 GPU 成本，全部数字可由一条命令重算：
> `python tools/necessity.py daima/sweep_512.log daima/sweep_512_S4.log`

---

## 0. 三句话结论

1. **512³ 上"联合决策"不必要**：`tile_only(S=1)` 与 `seq`（先选 tile 再选 S）都命中全空间
   最优（+0.0%），而模型的 joint 决策是 **+9.2%**（rank 3/48）。差值**全部来自 TK 选错
   （32 vs 64），不来自深度**。
2. **两份日志的逐配置漂移中位 +12.9%（范围 +4.6%～+22.3%）**：512³ 上任何 5% 级的
   "距优"结论都不可复现。这个尺寸不能作为证据尺寸（只有 64 块、23 µs、半机、launch 占比高）。
3. 根因可修且只需一行：模型对 **TK 零分辨率**（`chunks × copy` 与 TK 无关），补一条
   **每 chunk 加性固定开销 `cChunk`** 即可；`l1model --calib-chunk` 显示**任何
   `cChunk > 0` 都会让 512³ 翻到 `TK=64/S=2` = 实测最优**，而 4096³ 与 syrk 的决策不变。

**读法**：
- `seq` 两会话都 +0.0% —— **顺序决策就够**，联合没有必要（至少在这个尺寸上）。

- `max_tile` 类规则（"容量内最大的 tile"）灾难性（+394%），说明"可行性硬约束 + 打分"
  这套东西本身是有效的——**但有效的是 tile 选择，不是 depth 联合**。

（每配置 R≥5、round-robin、取中位数+区间），否则"rank 3/48、距优 +5.4%"这类数字
换个晚上就变成 +9.4%。

## 3. 根因：模型对 TK 零分辨率（一行可修）

`copy ∝ TK`（窗口含 TK），`chunks ∝ 1/TK`，故 `chunks × copy` 与 TK 无关：
TK=32 与 TK=64 在模型里**完全同分**，tie-break 按枚举序取先出现者（TK=32），
于是丢掉了实测的 1.3 µs（5%）。

物理上丢的是什么：**每 chunk 的固定开销**（syncthreads×2 + wait + cp.async 发射）。
v1.8.2 把它写成 `max()` 的下界（`Lcap = min(1739, copy+comp)`），在 `copy ≫ Lcap`
的大 tile 上完全不可见。改成**加性项**即可：

```
block += chunks * cChunk          # cChunk ≈ 160 ns（由 512³ 的 TK32→64 差 1.3 µs / 8 chunk 反解）
```

`python tools/l1model.py --calib-chunk`：

| cChunk | 512³ 决策 | 4096³ 决策 | syrk 决策 |
|---|---|---|---|
| 0（现状） | 64×64/TK**32**/S4 | 128×256/TK16/S3 | TK64/S4 |
| 80 | 64×64/TK**64**/S2 | 128×256/TK16/S3 | TK64/S4 |
| 160 | 64×64/TK**64**/S2 | 128×256/TK16/S3 | TK64/S4 |
| 240 | 64×64/TK**64**/S2 | 128×256/TK16/S3 | TK64/S4 |

- 512³ 翻到 **TK=64/S=2 = 会话 B 的实测最优（27.2 µs）→ 模型 rank 1/48**；
- 4096³ 不动（copy 3409 ns ≫ 160 ns，符合"大 tile 上该项可忽略"的物理预期）；
- syrk 不动（本来已是 TK=64）。

**代价**：512³ 的绝对预测从 4.169e4 变 4.305e4（+3.3%），而实测最优 27.2 µs，
偏差仍约 +58%（半机档的已知保守，与 cChunk 无关）。决策对、绝对值不改善——这与
"决策由流量结构决定、绝对值由标定决定"的分工一致，可如实写进论文。

## 4. 这对论文意味着什么（必须改写法）

### 4.1 "必要性"不能靠 512³ 撑，也不能靠"深度有收益"的说法

GEMM 上 tile 与 depth 在这套载具里是**替代品**：加大 TK 与加深流水都在提高
"计算/同步"比，达到同样效果（512³ 上 TK=64/S=1 就能压到 TK=32/S=4 的水平）。
所以"joint 优于单维"在满占用、搬运主导的配置上**本来就不该成立**——这不是实验没做好，
是物理。

### 4.2 主表按 regime 分层，而不是 11 行平铺

| regime | 判据 | 联合是否有意义 | 证据 |
|---|---|---|---|
| 搬运主导 + 满占用 | `comp/copy < 1` 且 `blocks ≥ SM` | **否**（depth 二值，tile 主导） | 512³/4096³ 的 S 平坦 + 本表 seq=oracle |
| 容量受限 | 大 tile/大 TK 下 `S` 被 99 KB 卡住 | **是**（tile 与 depth 通过容量耦合） | 4096³ 64×64/TK64 仅 S≤2（模型算得，待日志核） |
| 计算主导 | `comp/copy > 1`（A100/H100） | **是**（depth 有真实收益） | 待 A100 实测（P2） |
| 低占用 | `blocks < SM/2` | **是**（waves 少，深度换暴露延迟） | heat1d 2^20 / mvt T=8 |

这恰好把"必要性"从"每个 kernel 都需要联合"改成"**联合只在两类 regime 里成立，
而模型能提前判定是哪一类**"——比原写法更硬，也更难被打。

### 4.3 立即可做的两项（都是 CPU 侧）

1. **v2.0 加 `cChunk`**（一行）+ 全量回归；预期：512/500 翻到 TK=64，其余不动 → 需要 rebase 两个 golden。
2. **重测 512³**：交错重复（R=5）+ 中位 + 区间，重新判定会话 A/B 哪个是干净的；若漂移仍 >10%，把 512³ 从主表降为"小尺寸/低占用"案例，主证据换 1024³/2048³/4096³。
